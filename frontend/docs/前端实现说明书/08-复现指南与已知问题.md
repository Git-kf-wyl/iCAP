### 4.2 dataPipeline 路由断链（P0，页面 404）

**现象**：从「轨迹质检」页点击跳转，或直接访问
`/dataPipeline/collection`、`/dataPipeline/correction`，**匹配不到路由**。

**根因**：原 `AgenticDataFlywheel` 仓库 `router.ts` 中有：

```ts
{ path: '/collection', redirect: '/collection/tree-building' }
{ path: '/correction', redirect: '/correction/expert-action' }
```

迁移时**未带入**（见 06 文档第 12 节差异表 #9）。

**触发点**：

- `src/dataPipeline/views/QualityView.vue:129` —— `<router-link>` 指向 `/dataPipeline/collection`
- `src/dataPipeline/views/QualityView.vue:133` —— `router.push('/dataPipeline/correction')`

**同时**：`src/components/visualization.vue` 的菜单里，
`/dataPipeline/collection` `/dataPipeline/correction` `/dataPipeline/task-pool`
`/dataPipeline/model-training` 只作为 **`el-sub-menu` 的 index**（用于展开/高亮），
**不作为可点击路由**（见 `visualization.vue:324,342,310,360`）。
因此**只有 QualityView 的两个跳转会真正踩坑**。

**修复**（在 `src/router/index.js` 的 `children` 数组中补两条）：

```js
{ path: 'collection', redirect: '/dataPipeline/collection/tree-building' },
{ path: 'correction', redirect: '/dataPipeline/correction/expert-action' },
```

> 建议同时补齐 `task-pool` → `task-generation/generate`、
> `model-training` → `model-training/data-mixture`，与菜单语义一致。
> 注意：`visualization.vue:651-674` 的白名单数组已包含这些路径，无需改动。

### 4.4 `VITE_API_BASE_URL` 与 `/api` 代理的冲突（P0，dataPipeline 全部请求 404）

**机制**：

```ts
// src/dataPipeline/api.ts:1
const API_BASE = (import.meta.env.VITE_API_BASE_URL ?? '').replace(/\/$/, '')
```

- **未设置** `VITE_API_BASE_URL`（本仓库既无 `.env` 文件）→ `API_BASE = ''`
  → 请求走**同源相对路径**。
- 此时若请求路径以 `/api` 开头，会被 `vite.config.js:19-23` 的代理命中：

```js
'/api': {
  target: 'http://icap.rnd.huawei.com',
  changeOrigin: true,
  rewrite: (path) => path.replace(/^\/api/, ''),   // ← 剥掉 /api 前缀
}
```

**结果**：`/api/v1/xxx` 被改写成 `/v1/xxx` 转发到后端；
若后端 dataPipeline 接口**本身就以 `/api` 开头**（或不在该主机上），则 **404**。

**复现期修复（三选一）**：

1. **推荐**：在工程根目录新建 `.env.local`：

   ```bash
   VITE_API_BASE_URL=http://<后端主机>:<端口>
   ```

   这样 `API_BASE` 非空、请求为绝对 URL，**绕过全部代理**。

2. 修改 `vite.config.js` 的 `/api` 规则，去掉 `rewrite`。

3. 让后端在同主机暴露同路径（不改前端）。

> ⚠️ 生产构建（`dist/`）下**没有 Vite 代理**，因此
> **上线前必须设置 `VITE_API_BASE_URL`**，否则 dataPipeline 请求全挂。
> 这属于工程**唯一真正需要环境变量**的地方。

### 4.5 状态层问题明细

#### 4.5.1 `datasetStore.js` —— 对象用数组方法（P1，一调用即抛错）

```js
// src/stores/datasetStore.js:4-8   state
state: () => ({ ruler1Datasets: {}, ruler2Datasets: {}, ruler3Datasets: {} })
//               ^^^ 是对象，不是数组

// src/stores/datasetStore.js:43-47  addDataset
addDataset(dataType, dataset) {
    if (dataType === 'ruler1') {
        if (!this.ruler1Datasets.find((k, v) => dataset.k)) {   // ❌ 对象无 .find
            this.ruler1Datasets.push(dataset)                   // ❌ 对象无 .push
        }
    }
    ...
}
```

> ⚠️ **精确复述**：对象上确实没有 `.find`/`.push`，调用即
> `TypeError: this.ruler1Datasets.find is not a function`。
> 而"引用未定义变量"的是 **`updateDataset` / `removeDataset`**
> （`datasetStore.js:60-102` 附近），它们引用了**未声明的 `dataType`**，
> 以及回调里对 `dataset` 的越界使用 —— 属**死代码**，不调用不报错。

**修复方向**：把 `ruler*Datasets` 改成数组，或改用
`Object.values(state.ruler1Datasets).find(...)` 写法，并修正变量名。

> 若这些 action 从未被页面调用，可**保持原样**（属死代码）。

#### 4.5.2 `taskStore.js`（P2，死代码）

```js
// src/stores/taskStore.js:4-8
state: () => ({ tasks: [] })     // ← 只声明了 tasks

// 但 actions 里 (taskStore.js:22-80)
addDataset(dataType, dataset) {
    if (!this.ruler1Task.find(...)) { this.ruler1Task.push(dataset) }   // ❌ ruler1Task 不存在
}
removeDataset(id) {
    if (dataType === 'ruler1') { delete this.ruler1Task.id }            // ❌ 同样
}
```

**结论**：`state` 只有一个 `tasks` 数组，而后续方法整体照抄
`datasetStore`，引用了**从未声明的 `ruler1Task`/`ruler2Task`/`ruler3Task`**
以及未定义的 `dataType`/`dataset`。

**保持原样即可**：这些方法**没有任何页面调用**，属死代码，不影响运行。
仅真正被使用的是 `setTasks` 与 `getTasks`/`getTaskById`。

setMTDirectionD(...) {

#### 4.5.4 `aiModel.js` —— `applyDeployModels` 永远为空（P1）

```js
// src/stores/aiModel.js:70-75
setApplyDeployModels(list) {
  this.models = (Array.isArray(list) ? list.sort((a, b) => {
    return b.is_available === a.is_available ? b.status - a.status : b.is_available - a.is_available;

}
```

**问题**：函数名是 `setApplyDeployModels`，但赋值的字段是 **`models`**
（而非 `applyDeployModels`）。因此 `applyDeployModels` **永远不被写入**，
而 `models` 会被意外覆盖。

> ⚠️ 注意这是 **Options API 风格**（`this` 直接改 state），
> 与 `interpretation.js` 的 **mutations 风格**（`(state, payload)`）不同，
> 说明仓库是两种写法混用。复现时**保持原样**。

**修复**：把 `this.models = ...` 改为 `this.applyDeployModels = ...`
（同时确认页面读的是哪个字段，避免改完两边都不对）。

#### 4.5.5 同名 store 导出冲突（P2）

`src/stores/aiModel.js` 与 `src/stores/AISchool.js` **都导出 `useAIModelStore`**。
同一文件内同时导入必须用别名：

```js
import { useAIModelStore as useAiModelStore } from '@/stores/aiModel'
import { useAIModelStore as useAISchoolStore } from '@/stores/AISchool'
```

#### 4.5.6 store id 与文件名不符（P2）

`src/stores/deepResearchChat.js` 中 `defineStore('deepSearch', ...)`。
**devtools 中显示 `deepSearch`**，仅影响调试识别，不修亦可。

#### 4.5.7 Pinia / Vuex 双轨并存（设计问题，非 Bug）

`src/main.js:22-23` 同时注册：

```js
app.use(createPinia())
app.use(stores)        // Vuex
```

- Pinia：`aiModel`、`AISchool`、`datasetStore`、`taskStore`、`rankingStore`、
  `reportPreview`、`chat`、`agentChat`、`imageChat`、`AudioChat`、`videoChat`、
  `deepResearchChat` —— 共 12 个 store（见 03 文档）。
- Vuex：根 store + 4 个 module（`rankingScoreVuex`、`taskTable`、`resultTable`、
  `interpretation`）。

**复现时必须两套都装**，否则一半页面崩。

### 4.6 API 层问题明细

#### 4.6.1 `runService.js:25` —— `/v1/v1/` 双前缀（P0）

```js
// Constants.js
export const API_BASE_URL = URLS.BASE + '/v1/'   // 已含 /v1/
// runService.js:25
`${API_BASE_URL}/v1/run_mt`                       // ← 又加一次 /v1/
// 实际请求：http://icap.rnd.huawei.com/v1//v1/run_mt
```

**修复**：去掉模板串里多余的 `/v1`。
**若后端恰好兼容**（部分网关会归一化双斜杠），可保持原样。

> **复现者必须实测**该端点，其余端点均无此问题。

#### 4.6.2 `dataService.js:32-43` —— 4 个函数共用同一端点（需确认）

四个不同语义的函数都请求 `get_current_multi_full_res`。
**可能是后端设计如此**（一个端点返回多维度数据），也可能未实现完整。
**不改代码**，仅记录。

#### 4.6.3 `modelService.js:36` —— axios 参数位置错误（P1）

```js
axios.get(url, payload, DEFAULT_CONFIG)   // ❌ 第 2 参应为 config
```

`payload`（对象）被当作 `config`。若该配置无 `params` 字段，
**查询参数不会发出**。

**修复**：`axios.get(url, { ...DEFAULT_CONFIG, params: payload })`。

#### 4.6.4 `dataFactory.js:18` —— 定时器泄漏（P1）

```js
constructor() { this.timer = setInterval(...) }   // 无 clearInterval
```

单例化尚可，若被多处 `new` 则**定时器累积**。

**修复**：改为单例，或在 `dispose()` 中清理。

#### 4.6.5 `dataFactory.js:39-45` —— 请求逻辑被注释（需确认）

实际请求代码被注释掉，管理器**空转**。若对应页面需要该功能，
说明该页面当前**依赖 mock 或后端未接**。**不改**。

#### 4.6.6 全局缺失统一请求层（设计问题）

- 无 `axios.create()` 实例；
- 无请求/响应拦截器；
- 无 `Authorization` 头统一注入；
- 错误处理在各调用点重复。

**修复建议**：新建 `src/api/http.js`（工程当前**不存在**该文件）统一封装，
但会**改变错误抛出时机**，需逐页回归，**复现阶段不建议动**。

## 九、复现风险总结

| 风险 | 等级 | 说明 |
|---|---|---|
| **二进制资源缺失** | 🔴 高 | 07 文档中 P0 清单缺任一 → 构建失败或页面空白；**无法用代码生成** |
| **未跟踪资源未传递** | 🔴 高 | 仅从 Git 克隆**必然缺**约 30+ 个文件 |
| **依赖未写回 `package.json`** | 🟠 中 | `npm install` 看似成功，换机即崩 |
| **后端不可达** | 🟠 中 | 大量页面依赖硬编码内网 IP，**L2 无法复现** |
| **dataPipeline 请求 404** | 🟠 中 | 未设 `VITE_API_BASE_URL` 时必现 |
| **路由断链 2 处** | 🟡 低 | 仅影响 2 个跳转，修复成本极低 |
| **状态层笔误** | 🟡 低 | 影响局部功能，不影响构建 |

> **一句话结论**：
> 只要**完整拷贝 `src/` + `public/`（含未跟踪文件）**、
> **补装 3 个依赖并写回 `package.json`**、
> **可选设置 `VITE_API_BASE_URL`**，
> 本工程即可稳定复现到 **L1（可构建 + 可运行）**。
