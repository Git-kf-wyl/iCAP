# harness-bench 评测工程使用说明

> 面向「使用 harness-bench 评测工程跑评测、接入新 harness」的完整操作手册。
> 配套文档：`docker/README.md`（架构契约）、`docs/接入文档/openjiuwen接入.md`（接入新 harness 的实例）。

---

## 一、工程简介

harness-bench 评测「模型 × harness」组合在真实 agent 工作流里的效果。一个 agent 的表现不只取决于底层模型，还取决于 harness（管理上下文、工具、状态、约束、权限、轨迹、恢复的系统层）。

核心数据：

| 项 | 值 |
|---|---|
| 任务 | 300 道沙箱化离线任务：**274 通用 + 26 多模态** |
| 分类 | 6 大类（Software Engineering 81 / Business Operations 71 / Systems Engineering 65 / Research and Analysis 40 / Web Development 27 / Content Production 16） |
| 被测 harness | OpenClaw / Claude Code / Codex / Hermes / Nanobot / Goose / OpenCode（+ 自定义接入的 openjiuwen） |
| 评分 | 1,408 个计分模块 + 安全门槛，由隐藏逐题 oracle 在离线 grader 容器里检查 |
| Python | 3.10+（grader 镜像基于 python:3.10-bookworm） |

**关键设计**（和常见 benchmark 相反）：

```
harness = 镜像（固定，docker/harnesses/<id>/）
任务   = 数据（可变，tasks/<id>/ 目录包）
评分   = 独立 grader 容器（复用 harness-bench 的评分引擎）
```

即：**镜像方向是「harness 固定、任务挂载进去」**，不是「任务做镜像、harness 挂进去」。

---

## 二、架构概览（三件套 + proxy）

### 2.1 harness 镜像

每个被测 harness 一个 OCI 镜像（`docker/harnesses/<id>/`），结构是两段：

- **stage 1（task-toolchain）**：`python:3.12-slim-bookworm` + `docker/openclaw/requirements.lock`（17 包办公文档+测试工具链），所有 harness 共享同一份。
- **stage 2（harness agent）**：各自的基础镜像 + 装具体 agent（npm/pip）+ 一个 `entrypoint.sh`（`/opt/harness/bin/run`）。

### 2.2 任务数据

每道题一个目录 `tasks/<id>/`：

```
tasks/028-excel-like-cleaning/
├── instruction.md      # 题面（给 agent 的任务描述）
├── workspace/          # 初始工作区（agent 的起点）
├── task.yaml           # 配置（超时/产物清单/安全门槛/评分入口）
└── tests/              # 隐藏评分器（cases.yaml + test_outcome.py + ground_truth）
```

### 2.3 grader 容器

评分是独立的 grader 容器（`docker/grader/`），和 harness 镜像完全分开：

- grader 镜像 = 通用评分引擎（9 个 grading 模块 + `grade_entrypoint.py`），所有题共用。
- 每题评分标准 = 数据（`cases.yaml` + `test_outcome.py`），挂进 grader 的 `/hidden`。

### 2.4 per-trial proxy（模型访问）

controller 为每次 trial 启动一个本地 HTTP proxy（`ModelBudgetProxy`），harness 容器访问 proxy 而非上游模型：

```
harness 容器 ──> 本地 proxy（trial_base_url）──> 上游模型（--base-url + 注入 key）
```

好处：key 不进 harness、不进 provider traces、proxy 统一 enforce 温度/输出/turn 预算。

## 三、环境准备

### 3.1 Python 依赖

```bash
uv sync --extra dev
```

（controller 是 trusted 的 host 进程，需要 `PyYAML>=6.0`；Python <3.11 还需 `tomli`。）

### 3.2 docker

评测全程在容器里跑（harness + grader 都是容器），需本地 docker daemon。镜像分两类：

- **harness 镜像**：`docker/harnesses/<id>/Dockerfile`，build 一次后复用。
- **grader 镜像**：`docker/grader/Dockerfile`，本地 build（官方未发布 registry 镜像）。

### 3.3 模型端点

需要两个东西：

1. **上游模型端点**（`--base-url`）：真正的 LLM 服务（本地 vLLM 或云 MaaS）。
2. **上游 api key**（`--upstream-api-key-file`）：可选，若上游无鉴权可省略。

## 四、快速开始（跑一次评测）

```bash
cd harness-bench-main

# （可选）把 api key 写进文件
echo "<你的 key>" > /tmp/upstream_key.txt

python tools/run_benchmark.py \
  --base-url "$HB_MODEL_URL" \
  --model <模型名> \
  --upstream-api-key-file /tmp/upstream_key.txt \
  --harness openclaw \
  --workers 4 \
  --temperature 1
```

默认跑 `catalog/release.yaml` 指定的 active task set（当前 = `standard274`，即 274 道通用题）。

选别的 harness：`--harness`（`openclaw` / `claude-code` / `codex` / `hermes` / `nanobot` / `goose` / `opencode` / `openjiuwen`）。

## 五、命令参数详解（run_benchmark.py）

### 必填

| 参数 | 含义 |
|---|---|
| `--base-url` | 上游模型端点（HTTP(S) base URL） |
| `--model` | 模型名 |

### 选 harness / 选任务

| 参数 | 含义 |
|---|---|
| `--harness` | 被测 harness（choices 从 `SPECS` 动态生成） |
| `--tasks` | 逗号分隔的 task id 子集，如 `--tasks 028-excel-like-cleaning,008-db-doc-consistency` |
| `--task-set` | 命名子集（`catalog/NAME.yaml`），如 `--task-set standard274` |
| `--suite-root` | suite 根目录（含 tasks/ 和 catalog/，默认仓库根） |

task id 就是 `tasks/` 目录名。可用 task-set：`standard274` / `standard254` / `standard237` / `archive0`。

### 模型预算

| 参数 | 默认 | 含义 |
|---|---|---|
| `--max-tokens` | 32768 | 单次输出上限 |
| `--context-window` | 200000 | 上下文窗口 |
| `--max-agent-turns` | 150 | agent 最大轮数 |
| `--temperature` | 1.0 | 采样温度 |
| `--thinking` | high | 推理强度（off/minimal/low/medium/high/xhigh） |
| `--timeout` | — | 超时（默认用 task.yaml 的 timeout_sec） |

### 其他

| 参数 | 含义 |
|---|---|
| `--upstream-api-key-file` | 上游 api key 文件路径（一行） |
| `--workers` | 并发 worker 数 |
| `--harness-image` | 覆盖 harness 镜像名 |
| `--run-root` | 结果根目录（artifacts/evaluations/...） |
| `--shard-count` / `--shard-index` | 分片 |
| `--model-service-id` | 模型部署稳定标识（shard 合并用） |

## 六、接入新 harness（扩展点）

harness-bench 对「新增被测 harness」有 3 处扩展点，登记后 `--harness <新id>` 自动可用：

| 扩展点 | 位置 | 作用 |
|---|---|---|
| `SPECS` 字典 | `tools/harness_runtime.py:53-106` | 登记 HarnessSpec（image/协议/config 名/docker context） |
| `render_harness_config` | `tools/harness_runtime.py`（:182 起） | 为每个 harness 生成模型配置（末尾 raise，需加分支） |
| `docker/harnesses/<id>/` | 目录 | Dockerfile + entrypoint.sh |

CLI 的 `--harness` choices 是 `sorted(SPECS)` 动态生成的，所以只改 `SPECS` + `render_harness_config` + 镜像目录即可，**不动 `run_benchmark.py` 主流程、catalog、grader、task 数据**。

完整实例见 `docs/接入文档/openjiuwen接入.md`（含 entrypoint 契约、入口脚本绕审批、踩坑记录）。

### harness 契约要点（entrypoint 必须满足）

- 读 `HARNESSBENCH_PROMPT`（prompt 路径）、`HARNESSBENCH_CONFIG`（config 路径）
- 只写 `/workspace` 和 `/state`（`--read-only` 只读根文件系统）
- 跑**恰好一个 agent turn**，转发进程 exit code
- 模型凭证从 config 读（base_url/model），api_key 恒为 `local-vllm-no-auth`（访问本地 proxy）

## 七、模型访问架构（api key 为什么是文件）

harness-bench **没有** `--api-key` 命令行参数。api key 通过 `--upstream-api-key-file`（文件路径）传，由 controller 读、注入 per-trial proxy。

```python
# run_benchmark.py:2698-2708
model_proxy = ModelBudgetProxy(
    base_url,                       # --base-url（上游端点）
    upstream_api_key=upstream_api_key,  # --upstream-api-key-file 读的 key
    ...
)
trial_base_url = model_proxy.start()   # 起本地 proxy

# render config 时传给 harness 的是 proxy 地址，不是上游
config_text = render_harness_config(harness_spec, base_url=trial_base_url, ...)
```

所以 harness 容器里看到的 `base_url` 是 proxy 地址、`api_key` 是 `local-vllm-no-auth`，真实 key 由 proxy 转发时注入。好处：key 不进命令行、不进 harness、不进 provider traces。

## 八、常见坑与排查

### 8.1 模型端点 DNS（外部域名连不上）

`run_contract_round` 有 `--dns 127.0.0.1`（`harness_runtime.py:414-415`）劫持容器 DNS。harness-bench 原生假设模型是 host 上的 vLLM（走 `host.docker.internal:host-gateway`）。

**如果 `--base-url` 是外部域名（阿里云 MaaS `ws-*.maas.aliyuncs.com` 等），容器内可能解析不了**。排查：先确认容器内能否解析该域名；若不行，需要改 network/DNS 参数，或让模型走 host 网关。

### 8.2 镜像拉取慢/卡死

WSL docker 拉大镜像层走 mirror（1ms.run / daocloud）可能 0B 卡死（回源慢）。现象：`docker build` 卡在 FROM 层几十秒不动。

对策：复用本地已缓存的等价镜像作 base，或换 mirror / 手动 `docker pull` 后 build。

### 8.3 依赖版本冲突（verify_toolchain 失败）

`pip install` 某个 harness 的依赖时，可能升级 task-toolchain 锁定的 17 包版本，导致 `verify_toolchain.py` 报 `task toolchain version mismatch`。

实例：openjiuwen 依赖 `python-docx>=1.2.0`，把锁定的 `1.1.2` 升级到 `1.2.0`（见 `docs/接入文档/openjiuwen接入.md` 坑 2）。对策：跳过该 harness 的 verify 版本检查（功能向后兼容）。

### 8.4 只读根文件系统

harness 容器 `--read-only`，agent 运行时写的 `~/.cache`、`~/.config`、`~/.xxx` 都要指向可写位置（`/state` volume）。entrypoint 里设 `HOME` / `XDG_CACHE_HOME` 指向 `/state`。

## 九、评分链路（简要）

每道题一个循环：

```
加载 task 定义
  → 建 workspace/runtime/state
  → 渲染 prompt + config（base_url 指向 proxy）
  → 起 harness 容器（一个 turn）
  → 停 agent、hash 工作区（mutation 门槛）
  → 起 grader 容器（network=none、/workspace 只读）
  → 跑 oracle → result.json / summary
  → 销毁容器
```

评分字段：`outcome_score`（总分 0-1，各 case 加权）、`task_success`（是否过 pass_threshold）、`failed_contract_gates`（安全门槛）。详见 `docs/EVALUATION_AND_SCORING.md`。
